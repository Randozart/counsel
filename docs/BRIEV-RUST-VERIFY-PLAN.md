# Feasibility: A Cargo crate *written in Briev* that verifies Rust code

**Mode:** PLAN (research-first)
**Author's question:** "Can we feasibly create a Cargo crate written in Briev that helps do basic verification on Rust code the way Briev does it — with pre and postconditions, etc.?"
**Status:** Research complete. Verdict: **Feasible, but scope it correctly.** The pieces that are hard are not the ones that look hard.

---

## 0.1 Decision (owner: Randy) — 2026-11-11

**Proceed with Ambition A: runtime contract enforcement.**

Rationale, from the project owner:
- This is intended as a **stress test of the language**: `verify.bv` forces Briev's own contract/proof machinery through real, non-trivial code (a self-verifying verifier).
- It yields a **useful crate for ongoing Rust work** positioned as **substantially lighter than Kani** — Kani is a full model-checker/SMT harness over the whole Rust memory model; this is a pre/post-condition obligation checker with runtime enforcement plus a sampler. Different weight class, different promise. Eat that positioning explicitly.
- **B remains explicitly out of scope** for the first deliverable. Do not market static proof.

Scope guard retained: the crate ships *checks*, and its verification machinery is *authored in Briev à la A1 then A2*. "Verification the way Briev does it" = contract model + cross-verification sampler, transplanted to Rust at runtime — not Briev's compile-time prover over Rust source.

**Priority decomposition (revised):**
> A1 (Rust-closure obligations) → A2 (pure-Briev predicate AST) → sampler → stretch-B later, if at all.

---

## 0. Plain-language verdict

- **YES to the crate mechanically.** Briev already compiles to a linkable native static lib (`brievc build x.bv --library` → `libx.a`) and already ships a working **build.rs + `--library` + autogenerated bindings** integration that wires a Briev library into a Rust crate (`examples/glue-host/rust-host/`). Publishing a crate whose core logic is authored in Briev is not novel — the harness exists and is proven.
- **The hard part is "verification the way Briev does it."** Briev's deep verification (the `proof_engine`: symbolic SAT checks + Z3 SMT arbiter) runs *at compile time inside the compiler*, over Briev's **own AST**. It does **not** verify external Rust source — and the compiler has **no Rust parser** (no `syn`/`proc-macro` deps; it only lexes/parses Briev).
- Therefore there are two very different ambitions hiding in one sentence. Tell them apart up front:

| Ambition | Meaning | Feasibility |
|---|---|---|
| **A. Contract *enforcement* (runtime)** | A crate that lets Rust code declare pre/post conditions and *checks them* (panic / return Result / record failure) at runtime. | **Feasible now.** This is a portable obligation-checking library; Briev-side logic compiles to native, Rust-side is a thin macro/derive facade. |
| **B. Contract *proof* (static/verification)** | A crate that *proves* Rust contracts the way Briev proves its own contracts, without executing. | **Not feasible as "just write it in Briev."** Requires either re-expressing user Rust bodies into a verification IR (VC generation) or an SMT backdoor. This is a multi-person re-architecture, not a crate. |

The rest of this document argues for ambition **A** (runtime enforcement with a clear, honest path toward a slice of **B**), and shows exactly what the machinery does and doesn't give you.

## 1. What Briev's "verification" actually is (grounding)

Source of truth: `briev-lang/src/proof_engine/*` and `src/assertion_verify.rs`.

- Contracts are predicates (`[pre][post]`) attached to `node`/`txn`/`defn`.
- `proof_engine::prove_contract(pre, post, params, explicit)` runs at **compile time**, in the compiler pipeline (the `Verify` stage, `src/compile.rs`).
- It evaluates what it can **symbolically/heuristically** (`check_satisfiable`, `split_and`, bound propagation) and, when inconclusive, consults **Z3** (SMT, BitVec theory) as an arbiter. Z3 is optional; without it the heuristic verdict is final (violations deny, inconclusive allows).
- `assertion_verify.rs` handles one specific proof: `sig -> true` (function always returns Bool `true`).
- At **runtime**, verification is *not* re-done in general. There is **sampling/cross-verification** (`cross_verify_samples`, the `:=` shadow / reference chain) and a `fuzz_checker`, used to validate a compiled artifact against a reference — but this is a test-time cross-check, not a shipped static prover.

**Consequence:** "the way Briev does it" cannot literally be transplanted into a library crate, because the prover lives in the compiler and consumes Briev AST, not Rust source. What CAN be transplanted is the *contract model* (pre/post predicates over state), the *runtime cross-verification sampling* idea, and (with real work) a restricted VC generator.

## 2. The crate mechanics are proven (not speculative)

Evidence — `briev-lang/examples/glue-host/rust-host/`:

- `build.rs` runs `brievc build rank.bv --library --out $OUT_DIR/briev`, then:
  ```
  cargo:rustc-link-search=.../briev
  cargo:rustc-link-lib=rank
  cargo:rerun-if-changed=.../rank.bv
  ```
- `brievc bindings rank.bv rust` emits `src/briev_bindings.rs`: `extern "C"` fn decls + `#[repr(C)] struct BrievState`, `__briev_init_state()` / `__glue_release(state)`.
- `main.rs` calls it as plain C ABI: `add(3,4)`, `feature_hash(state, 1000, 42)`.
- `--library` emits **real ELF objects** (both a static `.a` and a PIC `.so`), rustc-linkable. Boundary types live in `glue/rust/types.bv` (`i64,f64,cstring,bool,char`); Rust path is "Path A LLVM LTO" (Briev `.ll` merges with host crate's `.ll`).

So: **a Cargo crate that, via `build.rs`, shells to `brievc` and links a Briev-authored library is a done pattern.** Publishing it to crates.io works if `brievc` is available at build time (same model as `bindgen` needing `libclang`, or `cc` crate needing a C compiler). `BRIEVC` env override already exists in the example.

## 3. The two ambitions, and the correct target

### Ambition A — Contract *enforcement* (runtime) — FEASIBLE, recommend MVP first

Goal: Rust users write `#[pre(...)]` / `#[post(...)]` (or a trailing macro/combinator form) on functions; the crate enforces them at runtime (panic, `Result`, or a failure log). This is "a Cargo crate written in Briev that helps do basic verification of Rust code, with pre and postconditions."

Layering:
- **Briev library (`verify.bv`)** — the actual verification core, authored in Briev:
  - A passable, copyable value model and a bound/environment that implements binding of the pre/post predicate variables.
  - `check_pre(predicate_inputs) -> bool`, `check_post(inputs, outputs, old_state) -> bool`.
  - An obligation evaluator that walks a small contract IR.
  - An error/failure reporter (message assembly).
  - Optionally the **cross-verification sampler**: given `original` and `shadow`/`reference` closures, run N interleaved samples and compare outputs (mirrors `cross_verify_samples`, `:=`). This is the piece genuinely "the way Briev does it" and it's portable.
  - All Briev-side logic itself carries Briev contracts — so the *verifier is verified*, dogfooding Briev.
- **Rust facade/macro** — thin; two options:
  1. **proc-macro / derive** (`#[contracts]` transforming `fn` into `fn_checked` with injected checks). Requires adding a `proc-macro` crate with `syn`/`quote` — trivial Rust, but note the compiler itself doesn't do this; this is a separate small Rust crate.
  2. **No macros**: a combinator API (`pre(x>0).then(f).post(...)`) plus a `check!` macro. Even simpler, zero new Rust beyond stubs.
- **Contract expression evaluation.** The crux of Ambition A is *where predicates get evaluated*. Two honest choices:
  - **Rust side evaluates**, Briev side provides the machinery/IR/roles. Predicates are Rust closures → called by Briev library through C ABI function pointers. Briev exports take fn-pointer params (supported: `Type::Function`).
  - **Briev side evaluates** the predicate AST (true "written in Briev" verification). Then the predicate must be expressed in Briev (a small DSL: `Greater(x,0) && Less(x,n)`), and Rust passes a serialized predicate AST. More "Briev," more faithful, more work and a marshalling cost.

Recommendation: ship **A1** (Rust-closure predicates, Briev provides IR + evaluator shell + sampler + reporter) as the honest MVP, then expose **A2** (Briev-side predicate AST) as the "pure Briev" flagship once A1 lands. A1 and A2 share all the Briev machinery; only the predicate transport differs.

### Ambition B — Contract *proof* (static verification) — STRETCH, not a crate

To actually *prove* arbitrary Rust functions against contracts at compile time "the way Briev proves its own code," you need a **verification-condition generator**: parse Rust → a VC/symbolic model → discharge via the existing `proof_engine`/SMT. Friction points, all real:

1. **Parser/AST gap:** compiler has no Rust frontend. Add `syn` to parse Rust and lift function bodies into a constraint form.
2. **Memory model:** Rust borrow/ownership, pointers, `&mut`. Briev's proof is over its own state vars, not raw Rust memory. Needs a heap/alias model.
3. **Soundness of the VC generator:** turning arbitrary Rust (control flow, recursion, aliasing) into obligations is a research-grade effort (cf. Kani, Creusot, Prusti). Not a weekend crate.
4. **Where it runs:** as a `build.rs`/proc-macro compile-time gate, or an LSP/CLI (the Praetor model).

A realistic *stretch slice* of B: restrict the surface (pure integer functions, no pointers, no recursion) and generate a VC from a small Rust subset that maps to Briev `Expr`/`proof_engine`. Even that requires the parser + VC generator; feasible as a prototype, not as a general crate.

## 4. Recommended phased plan

**Phase 0 — Spike the crate scaffold (proves the build path).**
- New crate `briev-check` (Rust + `build.rs`).
- Minimal `machinery.bv`: happy-path exports `add`, `checks_within`, a `pre_post` combinator.
- Wire exactly like `rust-host`. Gate via `BRIEVC`. Add `crates.io` packaging notes (system `brievc`, or vendor `brievc` over the existing `briev-compiler` crate).
- **Exit criteria:** `cargo test` runs a Briev-compiled export end-to-end.

**Phase 1 — Ambition A1 (Rust-closure predicates, Briev evaluator shell).**
- Briev: contract IR (`Contract { pre: fn, post: fn, name }`), `bind_env`, `eval_pre`, `eval_post`, failure reporter.
- Briev exports: `register_contract(name, pre_id, post_id)`, `run_checked(f_id, ...)`, `report_failures() -> String`.
- Rust: `#[contracts]` proc-macro (add a small `briev-check-macros` crate) or combinator API. Rust closures pass across as fn pointers.
- **Exit criteria:** user fn with `pre: x>0`, `post: ret>=0`; a violating call (a) runs the Briev check (b) panics/returns `Err` from Briev's reporter.

**Phase 2 — Cross-verification sampler (the "Briev does it" signature feature).**
- Port the `:=`/`cross_verify_samples` idea: `verify(original, shadow, n)` runs interleaved samples, compares (IO-equivalence), returns a verdict — the portable, high-value chunk of Briev's runtime story. Fits the crate narrative (a "shadow benchmark" harness for Rust, echoing Praetor's three-gate model).

**Phase 3 — Ambition A2 (pure-Briev predicate AST).**
- Add a tiny contract DSL: `pre(Gt(Var(x), Lit(0)))`, serialized to the Briev side and *evaluated in Briev*. Removes the "Rust closures do the checking" caveat, making the verification genuinely authored-in-Briev. Marshalling cost; keep A1 as the hot path.

**Phase 4 — stretch slice of Ambition B (optional / research).**
- Restricted Rust subset → VC → `proof_engine`/Z3. Prototype only. Do not market as general static verification.

## 5. Trade-offs & decisions to make

1. **Runtime enforcement vs static proof.** (Decided: runtime for the first deliverable; static proof is the deferred stretch, B-side only.) Everyone's expectations hinge on this. Ship A truthfully ("checks at runtime, verified-by-contract machinery authored in Briev"); be explicit that B is a research program, not the first crate.
2. **Who evaluates predicates** (A1 Rust-closures vs A2 Briev-AST). A1 ships faster and is hot-pathed; A2 is the flagship "written in Briev" claim. Shared machinery makes this a late, low-risk pivot.
3. **Macro vs combinator facade.** Proc-macro reads nicer (`#[pre(x>0)]`) and is the standard Rust ergonomics; requires a (trivial) `syn`/`quote` Rust crate. Combinators need zero new Rust. Do the macro; it's cheap and it's the part Rust users expect.
4. **`brievc` availability on crates.io users' machines.** Same maturity problem as `bindgen`. Document `BRIEVC`; consider vendoring a prebuilt `brievc` via the published `briev-compiler` crate's binary. This is the #1 practical packaging risk for actually publishing. (For the stress-test motivation this is irrelevant — the owner runs a local release `brievc`; it only matters at publish time.)
5. **Keep the verifier verified.** Briev-side logic with its own `[pre][post]` contracts is the differentiator and the right dogfooding story — but every unproven Briev contract on the path must be `[true]`-free, or the compiler rejects it (trivial contracts are compile errors). Budget time for satisfying Briev's own contract checker in `verify.bv`.
