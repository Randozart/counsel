republished. Registry: `counsel` latest 0.2.1, yanked `0.2.0`, `0.1.6`, `0.1.0`.

## The finding

`counsel 0.2.0` was published from commit `04bd7b5`. The only commit after it is:

```
5dbcd3b fix(static): restore call inlining, which went out with the text emitter
```

and the published tree proves it:

```
$ git show 04bd7b5:src/check/build.rs | grep -c inline_calls
0
```

**The crate on crates.io carries the exact regression the lab caught.** Call
resolution (`build_summaries` / `inline_calls`, with the R3 and R4 rules) is
absent, so `--features static` cannot verify a function that calls a helper.

### Impact, stated precisely

Not a soundness bug — the published crate never reports a false proof. It is a
functional regression:

| Source | Published 0.2.0 behaviour |
|---|---|
| a file whose only function calls a helper | `Err(Unsupported: ... a function call)` |
| a file mixing callers with other contracts | the caller is **skipped with a warning** and gets no verdict |

The `caller.rs` kernel — `uses_inc(a) = inc(a) + 1` with `#[post(term == a + 2)]`,
proved since lab slice 3 — is refused by the published crate.

### Why the acceptance did not catch it

The 0.2.0 acceptance (`/tmp/acc020`) proved a loop kernel, refuted a false
contract and checked a case. **It never exercised a call.** It passed, and the
regression shipped.

Two process gaps follow:

1. The acceptance set was not derived from the lab kernels — the thing that
   actually exercises the supported surface.
2. The acceptance procedure is not in the repository. `scripts/` holds only
   `publish.sh`; acceptance lives in `/tmp`, so it is neither reviewed nor
   repeated.

## Plan

### 1. Release 0.2.1 (counsel only)

Only `counsel` changed (`src/check/build.rs`, `src/check/inprocess.rs`, +219
lines). `counsel-macros` 0.1.1 and `briev-verify` 0.1.0 are already correct and
unchanged — do not republish either.

```bash
# bump counsel to 0.2.1, then:
./scripts/publish.sh          # skips the already-published companion
```

### 2. Yank 0.2.0

It shipped a feature broken for the common case, which is the same class as
`0.1.6` (invariants published against a pre-fix compiler) and `0.1.0`. The
project's precedent is to yank rather than leave a broken version resolvable by
anyone who pins it. `0.2.1` supersedes it for normal resolution, so yanking costs
nothing and prevents `=0.2.0` from being deliberately chosen.

### 3. Make acceptance versioned and lab-derived

Add `scripts/acceptance.sh` to `counsel`, runnable against a **published**
version, covering one case per supported construct — derived from
`briev-counsel-lab/labs/kernels/`:

| Kernel | Construct it pins |
|---|---|
| `caller.rs` | call inlining (R3/R4) — *the case this release exists for* |
| `loop_invariant.rs` | loop invariants, all three obligations |
| `dynamic_loop_invariant.rs` | dynamic bounds + `max` tail |
| `loop_sum.rs` | unrolled constant loop |
| a false contract | `Violated` still fails |
| a `#[case]` | `ProvenForCase` is not a general proof |

The script must `cargo add counsel@<version>` into a scratch project with no
`BRIEVC`, no sibling checkout and an empty cache, so it measures what a consumer
gets — not what the working tree does. That distinction is the whole lesson of
0.1.6, and 0.2.0 repeated it in a new form.

### 4. Gate the release on it

`publish.sh` should refuse when the acceptance script has not been run for the
version being published, or simply run it first. A release procedure that can pass
while a supported construct is broken is the defect behind both incidents.

## What this does *not* need

- No `briev-verify` or `counsel-macros` release.
- No Briev change: the fix is entirely inside `counsel`.
- No asset, no pinned toolchain — that machinery is gone.
